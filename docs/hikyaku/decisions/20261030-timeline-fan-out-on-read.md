# タイムラインは読み取り時に生成する

- **決定**: タイムラインは投稿の書き込み時に配らず、読み取り時にフォロー先と自分の投稿を `posts(author_id, id)` の索引で引き、ID による keyset ページングで返す
- **文脈**: フォローは最大5,000人、フォロワーは上限なし（5万人超もいる）。公開範囲の変更・フォロー解除・投稿削除が過去の投稿にも即時に反映される必要がある（US-5.2 / 11.3 / 11.6）
- **検討した案**:
  - 案A: 読み取り時に生成（fan-out on read）
  - 案B: 書き込み時に配る（fan-out on write）
- **採用理由**: 書き込みコストがフォロワー数に依存せず、可視性の判定を読み取り時に行うので遡及反映が自然に満たされる。ピーク毎分500件の読み取りなら 1 秒（p95）に収まる見込み
- **トレードオフ**: フォロー5,000人の読み取りクエリは重く、1年後の規模での性能テストで確認が要る。規模が数倍になったら、読み取りの最適化かキャッシュの追加が必要になる。fan-out on write は読み取りが速いが、フォロワー数に比例して書き込みが増え、遡及反映に再配布が要り整合性リスクが高いため退けた
- **影響範囲**: `apps/api` の投稿一覧クエリ、`posts` / `follows` の索引設計
